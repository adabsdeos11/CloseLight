# CloseLight

分析（为了节约时间和界面美观，部分内容实用AI编写）

## 我的判断

我看到的主要风险信号是：解析时使用的知识库基线越旧，人工质检打回率越高。知识库同步年龄超过 15 分钟的样本中，打回率为 42.5%；不超过 15 分钟时为 3.0%。相比之下，`confidence_score` 的分档打回率在 11.9%–14.5% 之间，接近整体 12.9%，单独用它标记低置信解析没有明显区分力。

因此，我把最值得先排查的根问题定为**知识库同步与查询执行之间的时序错位，或基线新鲜度不足**，而不是先调低置信度阈值。现有字段只能支持这一根因假设，不能判断究竟是同步延迟、队列等待还是知识覆盖变化；需要同步日志和一次干预试点才能确认机制与因果关系。

## 我做了什么

- 将 `query_time` 和 `kb_synced_at` 按各自时区解析，计算每条流水执行时的知识库年龄（分钟）。
- 检查重复行与标签缺失：原始 1,337 行中有 64 行是完全重复记录；去重后为 1,273 条，其中 1,223 条有质检结论（1,065 合格、158 打回），50 条仍未回传。重复的 `record_id` 没有字段冲突；未回传标签没有被当作通过或打回。
- 在前五个日期（9 月 1–5 日）上扫描 0–65 分钟阈值，13–16 分钟并列得到最高的假设净工时；选取 `知识库年龄 > 15 分钟` 作为单一、可复现的试点规则，再查看最后两个日期（9 月 6–7 日）的时间顺序检查。
- 按客户组拆开核对新鲜度关联。4 个客户组在超过 15 分钟后打回率明显升高；`数码数码组`没有出现相同趋势，因此试点应按组观察，不应把聚合规则当成每组都已证实的机制。

## 数据证据与预警价值

| 指标 | 结果 |
| --- | ---: |
| 原始行数 / 完全重复行 | 1,337 / 64 |
| 去重后的记录 / 已回传标签 | 1,273 / 1,223 |
| 已回传样本打回数 / 打回率 | 158 / 12.9% |
| 知识库年龄 `<=15` 分钟：打回 / 已回传 / 打回率 | 27 / 915 / 3.0% |
| 知识库年龄 `>15` 分钟：打回 / 已回传 / 打回率 | 131 / 308 / 42.5% |
| `>15` 分钟规则覆盖率 / 打回召回率 | 25.3% / 82.9% |
| 打回样本的知识库年龄中位数 / 合格样本中位数 | 36 / 8 分钟 |

时间顺序检查（9 月 6–7 日）中，整体 358 条已回传样本有 44 条打回，打回率为 12.3%；`>15` 分钟规则标记 76 条流水，其中 74 条已有标签、33 条打回、41 条合格、2 条未回传。已标记样本的打回率为 44.6%，捕获了该时段 75.0% 的打回。

### 工时口径

按题目给定口径，每条预警按 10 分钟计算，包括仍未回传质检结论的预警；每条被阻止的打回最多避免 90 分钟返工。时间顺序检查中，若干预能阻止 33 条已命中的打回，理论毛节省为 `33 × 90 = 2,970` 分钟；76 条预警成本为 `76 × 10 = 760` 分钟；理论净空间为 **2,210 分钟（36.8 小时）**。至少要实际阻止 9 条打回（27.3% 的 33 条命中）才覆盖这批预警的标记成本。

这不是已经实现的节省：历史数据没有干预前后对照，相关性也不等于因果。价值证据是该规则在最后两个日期仍集中命中打回，并且即使只避免约四分之一的命中打回也能覆盖标记成本。下一步应试点“同步/确认基线后再重跑”，逐条记录预警成本、重跑结果和最终质检结论，再核算实际净工时。

## 复现

仓库内的 `data/ai_eval_records.csv` 是本题提供的数据副本；我没有补造或并入外部数据。使用 Python 3（仅标准库）运行：

```bash
python3 analysis/analyze_records.py
```

脚本会打印数据校验、分档打回率、客户组拆分、训练期阈值扫描和最后两个日期的时间顺序检查。阈值扫描和“净工时”是分析假设，不是因果估计；成本公式为 `捕获打回数 × 90 - 全部预警数 × 10`，并假设每个被捕获的打回都能被干预阻止。详细交互与修订记录见 [`AI_LOG.md`](AI_LOG.md)。

## 后续验证

我会先将 `>15` 分钟作为候选提示，不自动判废。试点时优先核对知识库同步状态并重跑，按客户组分别统计结果；对 `数码数码组`保留观察，不据这批数据单独宣称知识库年龄是其打回原因。只有在试点中验证重跑能降低打回且实际节省工时大于 10 分钟标记成本后，才把它升级为稳定预警规则。
